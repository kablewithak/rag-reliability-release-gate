# Corpus Constitution

**Project:** RAG Reliability Release Gate  
**Constitution version:** 1.0  
**Status:** Frozen for V1  
**Governing source:** `PRD.md`  
**Snapshot descriptor:** `datasets/source_manifests/source_snapshot_v1.json`

---

## 1. Purpose

This constitution defines what may enter the V1 corpus, what counts as authoritative
evidence, how current and comparison source states are distinguished, how source
material is acquired and normalized, and how synthetic chaos material is prevented
from becoming authoritative evidence.

The corpus exists to support controlled RAG reliability, chaos, load, and recovery
experiments. Corpus curation must not become the project itself.

---

## 2. V1 Product Scope

V1 evaluates a named target contract:

```text
product=GitHub REST API
product_scope=api.github.com
target_api_version=2026-03-10
comparison_api_version=2022-11-28
```

The comparison version remains a real supported GitHub API version upstream. Within
this project it is classified as `historical_comparison` because V1's named target
contract is `2026-03-10`.

This classification is project-scoped. It does not claim that `2022-11-28` is globally
invalid or unsupported.

## 3. Frozen Upstream Sources

### 3.1 Authored explanatory documentation

Repository:

```text
github/docs
commit=ec3629a841129ae28189d7bb2274a7b3d40c5095
```

Eligible authored prose is restricted to:

```text
content/rest/about-the-rest-api/
content/rest/authentication/
content/rest/using-the-rest-api/
```

A Markdown file is not automatically eligible merely because it is under one of these
paths.

Excluded:

- files marked `autogenerated: rest`;
- generated endpoint-reference shells;
- unrelated GitHub product documentation;
- mutable default-branch content acquired without the frozen commit;
- files that retain unresolved GitHub Docs template/data directives after normalization.

### 3.2 Versioned endpoint contract

Repository:

```text
github/rest-api-description
commit=3cef12e8a02d612ad032473d4fb87266f2befeae
format=OpenAPI 3.0 bundled
```

Current target:

```text
descriptions/api.github.com/api.github.com.2026-03-10.yaml
blob_sha=a6c606f584dd8f7a17802a47ef8db8d167a44345
```

Historical comparison:

```text
descriptions/api.github.com/api.github.com.2022-11-28.yaml
blob_sha=88a3cc7326d6fd3968042dde112d1c4c838af5bc
```

Do not use `descriptions-next` in V1. It is outside the frozen V1 contract.

## 4. Endpoint Families

V1 endpoint-contract material is bounded to four semantic families:

```text
issues
pull_requests
repositories_and_repository_webhooks
actions
```

The ingestion implementation must derive and commit an explicit operation allowlist
from the pinned OpenAPI bundle before corpus ingestion is accepted.

Do not infer inclusion from an unverified tag name at runtime.

The operation allowlist must identify each accepted operation by stable fields such as:

```text
api_version
http_method
path
operation_id
semantic_family
```

Adding another endpoint family requires an ADR because it expands the V1 corpus scope.

---

## 5. Authority Model

Authority is typed and source-purpose-specific.

### 5.1 Current endpoint-contract authority

For endpoint shape and versioned machine-readable contract facts:

```text
authority_level=authoritative
source_state=current
api_version=2026-03-10
source_family=openapi_endpoint_contract
```

### 5.2 Current explanatory authority

For cross-cutting authored guidance such as authentication, versioning, pagination,
rate limits, and troubleshooting:

```text
authority_level=authoritative
source_state=current
source_family=github_rest_authored_guidance
```

### 5.3 Historical comparison authority

For the previous API contract used to create real version/freshness conflicts:

```text
authority_level=historical
source_state=historical_comparison
api_version=2022-11-28
source_family=openapi_endpoint_contract
```

Historical comparison material may be retrieved during chaos experiments but must not
silently outrank the named current target contract.

### 5.4 Source conflicts

Do not silently merge conflicting current and comparison facts.

A conflict must remain inspectable through provenance and source-state metadata so the
runtime can exercise its declared source-state policy and the evaluator can determine
whether the resulting behavior is safe.

## 6. Acquisition Rules

All authoritative upstream acquisition must be immutable and reproducible.

Required:

1. Pin repository commits.
2. Pin date-versioned OpenAPI filenames.
3. Verify acquired bytes against expected source identity before acceptance.
4. Record retrieval time during actual acquisition.
5. Record raw and normalized content hashes where both representations exist.
6. Fail closed on identity mismatch.

Forbidden:

- scraping whatever happens to be on `main` at run time;
- using an unversioned OpenAPI alias as release identity;
- accepting a redirected or changed source without hash/identity verification;
- silently replacing a missing frozen source with a newer source.

Raw upstream clones/bundles are local acquisition cache, not repository evidence.
They must live under:

```text
datasets/source_documents/_upstream_cache/
```

and must not be committed.

The committed evidence is the snapshot descriptor, manifests, deterministic acquisition
logic, normalized accepted corpus artifacts where appropriate, and integrity hashes.

---

## 7. Authored-Prose Normalization

Normalization must be deterministic.

For an eligible GitHub Docs Markdown source:

1. Parse frontmatter into source metadata.
2. Reject `autogenerated: rest` documents.
3. Resolve only supported GitHub Docs data/reusable references from the same pinned
   `github/docs` commit.
4. Preserve headings, lists, tables, and fenced code semantically.
5. Normalize line endings and insignificant whitespace deterministically.
6. Reject the document if unresolved GitHub Docs directives remain.
7. Hash the normalized representation.
8. Preserve the upstream path and commit SHA in provenance.

The V1 normalizer is not required to reproduce the entire docs.github.com renderer.
Unsupported directives fail ingestion for that document rather than being silently
dropped.

---

## 8. OpenAPI Normalization

The OpenAPI ingestion boundary must parse the frozen bundled YAML and emit deterministic
operation records.

Each operation record must preserve at least:

```text
api_version
http_method
path
operation_id
semantic_family
summary
description
parameter_contract
request_contract
response_contract
source_repository
source_commit_sha
source_blob_sha
source_path
```

Where a field is absent upstream, preserve that absence. Do not synthesize missing
contract facts.

Current and historical operation records remain separate records even when their text
is identical.

---

## 9. Source Manifest

The canonical source manifest is line-oriented JSON (`.jsonl`), one accepted source
record per line, validated against the project source-record contract when that
contract is implemented.

Every real accepted source record must include at least:

```text
source_id
source_family
source_url
source_license
retrieved_at
source_commit_sha_or_version
document_version
effective_from
effective_to
authority_level
source_state
product_scope
api_version_or_snapshot
content_sha256
title
topic_tags
data_role
```

The snapshot-level identity is stored separately in:

```text
datasets/source_manifests/source_snapshot_v1.json
```

This separation keeps the frozen upstream identity small and reviewable while allowing
the later accepted-source ledger to grow line by line.

## 10. Licensing and Attribution

### GitHub Docs content

Documentation/content sourced from `github/docs` is recorded as:

```text
source_license=CC-BY-4.0
```

Every derived committed artifact must retain sufficient provenance for attribution,
including source repository, upstream path or URL, and frozen commit.

### GitHub REST API description

OpenAPI material sourced from `github/rest-api-description` is recorded as:

```text
source_license=MIT
```

The project's attribution evidence must retain the upstream repository identity and
license reference.

Public reports/viewer artifacts must preserve source attribution appropriate to the
derived evidence they expose.

---

## 11. Synthetic Chaos Overlay

Synthetic material is never authoritative.

Every synthetic record must include:

```text
synthetic_overlay=true
authority_level=none
eligible_as_final_citation=false
eligible_as_gold_evidence=false
derived_from_source_ids
chaos_purpose
seed
scenario_id
```

Allowed purposes:

```text
semantic_distractor
neutral_filler
duplicate_evidence
metadata_mutation
controlled_conflict
context_order_mutation
malformed_record_fixture
dependency_fault_fixture
```

A synthetic overlay may influence retrieval/context pressure in a named experiment.
It may not become an authoritative answer source, gold evidence, or release citation.

Any code path that permits this is a release-integrity failure.

---

## 12. Data Roles

Every source/case/artifact must have one primary role from the PRD-controlled ledger:

```text
unit_fixture
corpus_source
historical_source
background_load_source
chaos_overlay
evaluation_development_case
intervention_tuning_case
held_out_release_case
load_test_replay_case
public_demonstration_artifact
```

Roles are not interchangeable merely because two artifacts contain similar text.

---

## 13. Chunking Boundary

This constitution freezes source acquisition and normalization, not the final retrieval
chunking configuration.

Chunking must be frozen and hashed before baseline characterization and must preserve
source provenance, authority, source state, API version, and parent-record identity.

Changing chunking after a baseline is measured creates a new retrieval configuration
identity and requires a new comparable run.

---

## 14. Acceptance Gate

Corpus ingestion is not accepted until all applicable checks pass:

```text
snapshot identity valid
source path eligible
license recorded
authority/source-state typed
normalization deterministic
unresolved directives absent
content hash present
data role valid
synthetic authority prohibition enforced
operation allowlist committed
```

Failure is explicit. Invalid or ambiguous records go to `datasets/rejected_cases/` or an
equivalent rejected-source evidence path; they are not silently repaired into the
authoritative corpus.

---

## 15. Change Control

A new ADR is required to change:

- target API version;
- historical comparison API version;
- upstream repository snapshot;
- source-family scope;
- authoritative-source definition;
- synthetic-overlay authority rules;
- committed licensing policy;
- mutable-vs-immutable acquisition rule.

Implementation details may evolve without an ADR only when they preserve these frozen
contracts and are verified by tests/evidence.
