# ADR-0002: Freeze GitHub REST Corpus Sources and Version Snapshot

**Status:** Accepted  
**Decision date:** 2026-09-05  
**Governing PRD:** `PRD.md`  
**Related constitution:** `docs/constitution/CORPUS_CONSTITUTION.md`

## Context

V1 requires a public, version-aware technical-documentation corpus capable of supporting
both semantic retrieval pressure and real freshness/version conflicts.

Using live documentation without immutable identity would make later baseline, chaos,
held-out, and release evidence non-reproducible.

Using all GitHub REST documentation would also violate the bounded V1 scope by turning
corpus curation into the project.

Inspection of the upstream `github/docs` repository also shows that endpoint-reference
Markdown is autogenerated. The raw endpoint-reference source files are therefore not a
reliable standalone representation of endpoint facts. GitHub's machine-readable REST
API description is the appropriate versioned endpoint-contract source.

## Decision

### Target contract

Freeze the V1 target to:

```text
GitHub REST API
product=api.github.com
api_version=2026-03-10
```

### Historical comparison

Freeze the comparison contract to:

```text
api_version=2022-11-28
```

The comparison version is classified as `historical_comparison` only relative to the
V1 target. The ADR does not claim it is globally unsupported.

### Authored documentation snapshot

Freeze:

```text
repository=github/docs
commit=ec3629a841129ae28189d7bb2274a7b3d40c5095
license_for_documentation_content=CC-BY-4.0
```

Eligible authored prose is restricted to current REST guidance under:

```text
content/rest/about-the-rest-api/
content/rest/authentication/
content/rest/using-the-rest-api/
```

Autogenerated endpoint-reference files are excluded as prose corpus sources.

### Endpoint-contract snapshot

Freeze:

```text
repository=github/rest-api-description
commit=3cef12e8a02d612ad032473d4fb87266f2befeae
format=OpenAPI 3.0 bundled
license=MIT
```

Current target file:

```text
descriptions/api.github.com/api.github.com.2026-03-10.yaml
blob_sha=a6c606f584dd8f7a17802a47ef8db8d167a44345
```

Historical comparison file:

```text
descriptions/api.github.com/api.github.com.2022-11-28.yaml
blob_sha=88a3cc7326d6fd3968042dde112d1c4c838af5bc
```

`descriptions-next` is excluded from V1.

### Endpoint-family scope

Freeze four semantic families:

```text
issues
pull_requests
repositories_and_repository_webhooks
actions
```

The ingestion implementation must generate an explicit, reviewable operation allowlist
from the pinned bundles. Runtime tag guessing is not an accepted selection mechanism.

### Acquisition and normalization

- upstream identity is commit-pinned and version-pinned;
- raw upstream downloads are local cache and are not committed;
- authored prose is normalized deterministically and rejected if unresolved docs
  directives remain;
- OpenAPI is parsed into deterministic per-operation records;
- current and historical records remain distinct;
- source and normalized hashes are evidence;
- manifests are JSONL at source-record level with a separate frozen snapshot JSON.

## Why this option

This gives V1:

- real public provenance;
- a current named target;
- a genuine prior API contract for freshness/version chaos;
- machine-readable endpoint truth;
- authored explanatory prose for cross-cutting behavior;
- enough semantic overlap for retrieval pressure;
- bounded scope;
- reproducible source identity.

It also isolates version pressure without requiring an arbitrary web scrape or a
synthetic stale-document claim.

## Alternatives considered

### A. Scrape live docs.github.com

Rejected.

Mutable content would make evidence time-dependent and harder to reproduce.

### B. Use all of github/docs

Rejected.

The scope is unnecessarily broad and endpoint pages are generated from other source
material.

### C. Use only OpenAPI

Rejected.

OpenAPI is strong for endpoint contracts but does not replace explanatory guidance for
authentication, pagination, rate limits, versioning, and troubleshooting.

### D. Use synthetic stale documents only

Rejected.

Synthetic overlays are useful chaos controls but must not replace real version-state
evidence.

### E. Use `descriptions-next` OpenAPI 3.1

Rejected for V1.

The stable 3.0 descriptions provide the smaller, lower-change correctness surface needed
for this project.

## Consequences

### Positive

- release evidence can name exact upstream identities;
- current-vs-comparison conflicts are reproducible;
- corpus scope stays bounded;
- provenance and licensing are explicit;
- generated endpoint Markdown is not mistaken for authoritative source content.

### Trade-offs

- ingestion must implement two normalization paths: Markdown guidance and OpenAPI;
- GitHub Docs template references require bounded resolution or fail-closed rejection;
- operation-family selection requires a committed allowlist;
- current-vs-comparison case quality still needs to be demonstrated empirically before
  those cases enter the evaluation suite.

## Non-claims

This ADR does not claim:

- the selected families cover the entire GitHub REST API;
- `2022-11-28` is unsupported;
- every selected operation differs across versions;
- the corpus is already ingested;
- chunking is already frozen;
- evaluation cases already exist;
- the RAG system is implemented.
